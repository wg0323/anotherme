# 通用要求
- 所有文档使用 Markdown 格式，文件编码 UTF-8，换行符统一 Unix(LF)。
- 使用简洁、清晰的语言。
- 文档内容应保持最新：每次代码变更需同步更新对应文档；废弃文档移至 `deprecated/` 或标注 `@deprecated`。
- 避免拼写和语法错误。
- 使用中文作为主要语言，技术专有名词可保留英文。
- 文件命名：全小写英文 + 连字符（如 `api-guide.md`），禁止中文文件名。

# 目录结构
- `README.md`：项目根目录，提供项目概述。
- `CHANGELOG.md`：项目根目录，记录版本变更。
- `doc/`：存放详细文档。
  - `guide/`：使用指南。
  - `api/`：API 文档。
  - `examples/`：示例代码文档。
  - `requirements/`：产品需求文档。
  - `images/`：文档引用的图片资源。
  - `architecture/`：架构设计文档（可选，中大型项目建议添加）。

# README.md 内容规范
- 项目名称和简短描述。
- 技术栈说明。
- 环境要求与前置条件。
- 快速开始（安装 → 配置 → 运行）。
- 项目结构说明。
- 使用说明（核心功能演示）。
- 如何贡献（贡献指南）。
- 许可证信息。

# 版本记录规范
- 使用 `CHANGELOG.md` 记录版本变更，格式参考 [Keep a Changelog](https://keepachangelog.com/)。
- 遵循语义化版本（Semantic Versioning）规范。
- 每个版本必须标注发布日期（格式：`YYYY-MM-DD`）。
- 每个版本按以下分类记录变更：
  - `Added`：新增功能。
  - `Changed`：功能变更。
  - `Deprecated`：即将废弃的功能。
  - `Removed`：已移除的功能。
  - `Fixed`：修复问题。
  - `Security`：安全修复。
- 不兼容变更（Breaking Changes）需在版本号与分类中显著标注，并在正文中用 **BREAKING** 前缀说明影响范围。

# 文档内容组织
- 从整体到局部，从简单到复杂。
- 重要信息放在前面。
- 相关内容应当放在一起。
- 使用小标题和列表增强可读性。
- 单段不超过 5 行；超过 3 个并列点使用列表。
- 架构图优先使用 Mermaid 代码块（内嵌于 Markdown）；截图存放于 `doc/images/` 目录，使用相对路径引用。
- 文档中的外部链接应定期检查有效性，避免死链。

# 代码示例规范
- 所有代码块必须标注语言类型（如 ```java、```json、```bash），禁止无语言标注的裸代码块。
- 示例代码应尽量独立可运行；依赖外部服务（数据库、中间件等）时需在注释中说明前置条件。
- 代码应当简洁且易于理解。
- 添加适当的注释解释关键部分。
- 说明代码的预期输出或行为。
- 更新示例以匹配最新 API。
- 复杂规范建议同时给出 ✅ 正确示例 和 ❌ 错误示例，形成对比便于理解。
