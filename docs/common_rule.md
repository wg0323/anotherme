## 通用规则

- 始终使用中文回复用户，但技术专有名词可保留英文（如 API、Python等）。
- 需求落地与技术方案设计（搜索先行、开源选型）遵循 `solution-design` 技能。

## 前端默认技术栈

- 新建或改造前端时默认固定为：PC 管理后台 `Vue 3 + Element Plus`；移动端（H5 / 小程序 / App 一套代码）`uni-app + uview-plus@3.8.138`（锁定最后一个 MIT 版本，不升级、不买授权）；Windows 桌面小工具 `Tauri 2 + Vite + Vue 3 + TypeScript + Naive UI`（不引 Electron）。完整选型、起步模板与禁止项遵循 `frontend-stack` 与 `desktop-stack` 技能。
- 仅当用户明确指定其他技术栈、或存量项目已用别的栈（以现有栈为准）时才偏离，不因“更先进/更流行”自行换栈。

## 界面效果图确认门禁（强制）

新建或改造下列界面类项目前，必须先产出静态效果图并取得用户明确确认：小程序（微信原生 / uni-app）、涉及界面的 SpringBoot 管理后台、Windows 桌面小工具。

- **效果图指静态 HTML 页面，不是图片**：必须交付可直接用浏览器打开的 `.html` 文件（配套 CSS，必要时少量原生 JS 呈现关键交互状态），多页面项目每页一个 HTML 文件并互相链接，数据写死在页面里；不得用 PNG/JPG 截图、设计稿导出的图片、原型工具截图或 Markdown 线框代替。覆盖本次需求涉及的全部页面与关键交互状态；不接真实后端、不写业务逻辑。
- 收到针对当前版本效果图的明确确认前，只允许需求梳理、技术选型、数据模型与接口草案；禁止搭建实际工程、编写页面或后端业务代码。
- 效果图每轮调整后都要重新确认；未收到明确确认不得进入实际开发，确认后需求或视觉方向变化时回到效果图阶段重新确认。

## 规范技能加载

- 产出、修改或审查对象前，按对象类型与各技能的 `description` 加载匹配正文；不得以“任务很小”或“内容已掌握”为由跳过。
- 实现阶段只加载当前技术栈及其明确要求的前置技能。`test-execution`、`code-gate`、`gitflow` 分别在测试、交付、提交阶段加载，不在任务开始时整套预载。
- 技能正文每次会话只加载一次；references 按场景读取。交叉引用表示进入对应职责阶段时遵循，不等于立即加载被引用技能及其全部引用文件。加载一次不等于核对一次：每次阶段切换都必须重新核对绑定表，核对不要求重读全文。
- 多个技能命中不同维度时分别遵守；同一维度冲突时按下方「冲突停机上报」处理，不得自行按项目现有配置取舍，不重复执行等价自检。
- 匹配技能未安装时按名称提示用户，不得静默跳过后自行发挥。

## 技能门禁与冲突裁决

### 权威层级（冲突时按序裁决）

1. 用户当轮明确指令（含用户已确认的方案与计划文档）
2. 规范技能的核心铁律
3. 计划文档中未经用户确认的实现细节
4. 项目现有代码风格与惯例
5. 模型自身偏好

低位不得覆盖高位。第 1 条与第 2 条冲突时不适用“高位胜出”，必须走冲突停机。

### 冲突停机上报（强制）

出现下列任一情形，立即停止相关部分的实现，列出冲突交由用户裁决；禁止自行选择任一方，禁止“先做了再说明”：

- 用户指令或计划文档 与 技能核心铁律 冲突（例：计划要求 Flyway，springboot-spec 铁律禁止）
- 两个技能的核心铁律互相冲突
- 技能铁律与项目现状冲突（例：要求构造函数注入，存量全是字段注入）

输出格式：

```text
【冲突】<一句话说明>
- A 方：<要求>（出处：文件 / 章节 / 条款 ID）
- B 方：<要求>（出处）
- 影响：按 A 做会怎样 / 按 B 做会怎样
- 候选：①按 A，记入台账为已裁决偏差 ②按 B ③其他
```

未获裁决前只推进与该冲突无关的部分。

### 技能绑定（强制）

涉及产出或修改对象的任务，在动手前与每次阶段切换时，必须重新输出技能绑定表并核对本次要遵守的条款。阶段切换指：数据层→服务层→接口层、后端→前端、实现→测试、测试→交付。不得以“会话开头已加载过”为由跳过后续阶段的绑定。

台账每行只能落三态之一：遵守（给文件与位置）/ 不适用（给触发条件不成立的事实）/ 偏差（给理由、影响与用户裁决）。判“不适用”不得以“存量工程”“已批准的设计”“任务很小”“只是改几行”为据。

绑定表与台账的格式、模板与判定细则遵循 `spec-gate` 技能；该技能未安装或未加载时按本节要求自行维护同等内容。

### 完成定义（强制）

任务完成不等于测试通过加计划复选框打勾。同时满足以下三条才算完成：

1. 功能验收标准通过
2. 规范偏差台账中无“待裁决”项；偏差项均已获用户裁决并记录
3. 交付证据按 `code-gate` 格式给出，其中包含一行规范偏差结论

## 外部信息检索

**需要外部权威信息时：先查官方来源；官方结果不理想时，才降级参考辅助性质的博客/社区文章。**

- 适用场景、来源优先级与检索细则遵循 `external-research` 技能。

## 代码质量

### 编码前先梳理思路

**不主观臆断、不掩饰疑问、主动说明方案优劣取舍。**

动手实现前，遵守以下要求：

- 明确说出你的预设条件，存在不确定点就主动提问；
- 若需求存在多种解读方式，全部罗列出来，不要私自选定一种；
- 若有更简洁的实现思路，主动说明；必要时提出优化建议；
- 遇到模糊不清的地方立刻停手，指明疑点并向用户确认。

### 主动说明生产级/业界主流方案

**当交付的方案因 demo、本地硬件、快速验证等原因而非生产级或业界主流做法时，必须额外用文字说明真实生产环境/业界主流是怎么做的。**

- 适用判断：只要交付实现与生产实践存在**实质性差距**就要说明，典型如架构分层、技术/中间件选型、数据持久化、并发与一致性、部署运维、安全、可观测性等；对无关紧要的琐碎片段不必强行附注。
- 说明要点：主流方案采用什么技术/架构、为何这样选、与当前简化方案的关键差异、若要上生产还需补齐哪些环节。
- 交付方式：即便用户明确只要 demo，也要主动附上这段说明，无需用户追问；用简洁文字表达，不喧宾夺主。
- 边界：只做"文字告知"，不擅自把 demo 改写成重型生产方案，也不因追求生产级而违背用户"只要简单示例"的诉求。
- 涉及完整需求落地/技术选型时，对照说明的具体维度遵循 `solution-design` 技能。

### 优先保证代码简洁

**只写刚好能解决问题的最少代码，不添加无依据的拓展逻辑。**

不实现需求以外的额外功能；

- 仅单次使用的代码，不额外封装抽象层；
- 需求未要求时，不额外增加可配置、可扩展的冗余设计；
- 无需为理论上不可能出现的场景编写异常处理；
- 若写出 200 行代码，但该逻辑 50 行就能完成，必须重构精简。

自我校验：资深工程师会不会觉得这段代码过度复杂？如果答案是肯定的，就简化代码。

**边界**：匹配的技术规范仍需加载，但只读取当前任务所需内容，不重复加载或执行与改动无关的验收动作；高风险改动不得借“控制成本”降低验证等级。

### 精准局部修改

**只改动必要代码；仅清理自身修改产生的冗余内容。**

修改已有代码时：

- 不擅自优化无关代码、注释、代码格式；
- 不对无故障的逻辑做重构；
- 统一沿用项目现有代码风格，即便你有不同编写习惯；但与规范技能的强制条款冲突时，以技能为准；
- 发现无关的废弃代码仅做标注提醒，不要直接删除。

若你的修改产生了废弃内容：

- 仅删除因本次改动而不再使用的导入、变量、函数；
- 原有项目里的废弃代码，无用户指令则不做删除。

校验标准：每一行改动的代码，都能直接对应上用户的需求。

### 以目标为导向执行开发

**先定义完成标准，循环开发直至验证通过。**

将需求转化为可验证的明确目标：

- "增加参数校验" → 编写非法入参测试用例，再实现逻辑使用例通过；
- "修复 bug" → 先编写可复现问题的测试，再修复代码使测试通过；
- "重构 X 模块" → 保证重构前后所有测试均可正常运行。

多步骤任务需先列出简要执行计划：

```reStructuredText
1. [步骤] → 验证标准：[校验点]
2. [步骤] → 验证标准：[校验点]
3. [步骤] → 验证标准：[校验点]
```

清晰可落地的完成标准，能让开发流程闭环自校验；模糊标准（如 "能跑通就行"）会需要反复沟通确认。

## 安全规范

### 安全

- 绝对禁止修改、升级、降级、卸载、安装任何**系统级/全局**软件、工具、依赖、环境（包括但不限于 Python、Node、Java、Git、IDE、编译器、系统工具、数据库、环境变量、配置文件）。**项目级私有依赖拉取与本地构建缓存操作不受此限**。
- 绝对禁止修改本地系统配置、软件配置、环境变量、PATH、shell 配置、IDE 设置。
- 绝对禁止执行任何会改变本地环境状态的命令、脚本、操作；**唯一例外是你自产对象的收尾清理**（见下节）。
- 绝对禁止推荐、要求用户修改本地环境、配置、软件版本。
- 绝对禁止自动替换、修改用户本地已存在的配置文件。

### 会话收尾清理（自产自清）

**你启动的应用服务与产生的文件，必须在最终答复前清理干净，不留给用户收拾。**

- 必清：应用服务进程及子进程（`java -jar`、`mvn spring-boot:run`、`npm run dev` 等）、临时脚本、日志、临时文件与目录。
- 中间件按归属处理：既有或共享的数据库、消息队列、缓存不停；本次启动的专用临时实例须停止并释放资源，答复中写明状态。自动化测试数据按框架回滚或清理，手工验证的诊断数据保留供复查，会污染下次运行时提示用户。
- 不动：用户既有文件与用户启动的进程；构建产物（`target/`、`node_modules/`、`dist/`）保留，删除只会拖慢下次构建。
- 顺序与例外：先记录验证结论再清理；用户明确要求保留的，答复中写明端口与停止方式。
- 归属：终止进程前核对 PID 的命令行确为本次启动；**禁止按映像名批量终止**（`taskkill /IM java.exe /F` 会误杀用户其他 Java 程序与 IDE 语言服务器），归属不明不动手。
- 命令与完整清单见 `test-execution` 技能的 `references/cleanup.md`（未安装时按本节处理）。

### 授权豁免白名单（无需主动询问用户授权即可建议、生成并指导使用）

下述命令仅用于**查看信息、编译打包、项目级依赖拉取、项目构建、版本查询**等只读/项目常规构建行为，无需额外申请授权：
1. JDK 原生常用命令：`java`, `javac`, `jar`, `jps`, `jstat`, `jmap`, `javadoc`, `keytool` 等；
2. Maven 标准项目生命周期命令：`mvn clean`, `mvn compile`, `mvn package`, `mvn install`（仅限当前项目产物安装至本地仓库）, `mvn test`, `mvn dependency:tree` 等；
3. **其他主流构建工具的项目级命令**：`gradle build/test`, `npm ci`, `pnpm install`, `go build/test`, `cargo build/check` 等**仅作用于当前项目目录**的指令；
4. 若上述豁免命令涉及强制修改全局环境、删除非项目文件、覆盖系统级配置等高风险行为，依旧必须提前向用户确认授权。
