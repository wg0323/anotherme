# RESTful API 设计

## URL 设计原则

- **强制**：URL 中使用名词表示资源，使用复数形式。
- **强制**：URL 中禁止包含动词，动作通过 HTTP 方法表达。
- **强制**：URL 中使用小写字母，单词间用连字符 `-` 分隔。

## HTTP 方法使用

| HTTP 方法 | 操作类型     | 语义幂等           | 幂等键     | 示例              |
| --------- | ------------ | ------------------ | ---------- | ----------------- |
| `GET`     | 查询资源     | 是                 | 不需要     | 获取用户列表/详情 |
| `POST`    | 创建资源     | 否                 | 必须（认证类除外） | 新建用户          |
| `PUT`     | 全量更新资源 | 是                 | 必须       | 更新用户全部信息  |
| `PATCH`   | 部分更新资源 | 是（增量操作除外） | 必须       | 更新用户状态      |
| `DELETE`  | 删除资源     | 是                 | 不需要     | 删除用户          |

## 写接口的幂等契约

`POST`/`PUT`/`PATCH` 业务写接口一律要求客户端携带 `Idempotency-Key`，服务端按 `idempotency.md` 落地，不因 `PUT` 或按幂等方式设计的 `PATCH` 的“语义幂等”而省略：语义幂等只保证重复执行结果相同，不保证扣库存、发通知、记流水等副作用只发生一次。

- 幂等键缺失或格式非法返回 `400`；同 key 不同请求指纹（method、URI、query、客户端摘要任一变化）返回 `422`；处理中或首次结果未缓存返回 `409`。
- 带 body 的写接口还必须携带 `Content-Digest: sha-256=:<base64>:`（RFC 9530），否则 `400`；body 变化时必须按实际发送的新 body 重新计算摘要。
- 服务端不读请求体，只把客户端摘要纳入请求指纹。只改 body 而沿用旧摘要时，服务端无法识别变化，会按重放返回首次结果；客户端禁止复用旧摘要或手写常量摘要。
- 同 key 同指纹重放返回首次结果，业务不再执行；业务异常时释放键，允许同 key 重试。
- 认证类 `POST`（登录、登出、刷新令牌、验证码发送/校验、密码重置）不接入，避免缓存短期凭证或一次性码；它们按 `security.md` 做限流与冷却。
- 幂等接口成功时统一返回 `200`，不使用 `201`/`204`；成功响应不使用 `ResponseEntity`、`@ResponseStatus`，也不使用异步返回。

## HTTP 状态码规范

| 状态码                      | 含义       | 使用场景                               |
| --------------------------- | ---------- | -------------------------------------- |
| `200 OK`                    | 成功       | GET 成功；幂等写接口（POST/PUT/PATCH）成功与重放；DELETE 成功 |
| `201 Created`               | 创建成功   | 保留语义；POST/PUT/PATCH 接口接入幂等后不使用 |
| `204 No Content`            | 无内容     | 保留语义；DELETE 可用，POST/PUT/PATCH 接口接入幂等后不使用 |
| `400 Bad Request`           | 请求错误   | 参数校验失败、格式错误                 |
| `401 Unauthorized`          | 未认证     | 未登录或 Token 无效                    |
| `403 Forbidden`             | 禁止访问   | 无权限访问该资源                       |
| `404 Not Found`             | 资源不存在 | 资源不存在                             |
| `409 Conflict`              | 冲突       | 资源已存在、版本冲突、幂等键处理中/首次结果未缓存 |
| `422 Unprocessable Entity`  | 无法处理   | 业务规则校验失败、幂等请求指纹不匹配   |
| `500 Internal Server Error` | 服务器错误 | 系统内部错误                           |

> 注：本规范要求所有 `POST`/`PUT`/`PATCH` 业务写接口接入幂等，这三类接口成功时统一返回 `200`，不再使用 `201`/`204`；DELETE 仍可按语义返回 `204`。幂等接口文档按 `200` 编写。
