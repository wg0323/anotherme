# 真人风格写作规范（唯一真相源）

生成或改写任何 Markdown 文档时都必须遵循本文件。`readme-template.md`、`changelog-template.md`、`docs-structure.md` 管"写什么、放在哪"，本文件管"怎么写"——语气、用词与真实感。两者冲突时：结构以对应模板文件为准，语言以本文件为准。

> AI 文档为什么一眼能认出来：模型默认写给"最广泛的读者"，每个词都选统计上最稳妥、最普适的说法——稳，但平，且看不见具体的人。真人写给一个具体的读者、一个具体的场景。所以贴近真人不是把文档写口语化，而是补回具体：谁在读、解决什么真实问题、真实的命令与输出。

## 一、核心规则

### R1 先定读者与收益，再动笔

- 动笔前先回答两个问题：谁读这篇文档？读完能做成什么事？
- 技术指南/教程的第一段直接给收益，不写行业背景铺垫。
  - ❌ 随着消息中间件技术的不断发展，消息可靠性越来越受到重视……
  - ✅ 这篇指南解决 RabbitMQ 消费失败后消息丢失的问题。读完你会得到一套可直接套用的重试 + 死信队列配置，以及验证它是否生效的方法。
- 全文围绕"读完能做成什么"取舍内容，与这个目标无关的概念科普删掉。

### R2 具体优先于概括

- 写真实版本号、真实路径、真实报错文本、实测数字。禁止 xxx、foo、bar、示例值、"待补充"等占位符。
- 效果用数字说话："无索引时查询耗时 1.8s，加上复合索引后降到 30ms"，而不是"性能得到了显著提升"。
- 报错贴原文，不要转述："启动时报 `Communications link failure`"，而不是"启动时报了一个数据库连接错误"。

### R3 每个概念绑定真实场景

- 配置项、API、设计方式，都要回答"什么情况下用、不用会怎样"。
- 例：写死信队列，先说清场景——消息重试 3 次仍失败后不能丢，要进死信队列等待人工处理，否则这段逻辑没有存在理由。

### R4 承认局限与坑

- 写清适用范围和前置条件："以下步骤在 MySQL 8.0 + JDK 17 上验证过"。
- 已知的坑直接写出来，包括试过但没用的方案："先用 X 方案试过，高并发下会 Y，所以换成了 Z"。
- 不确定的地方如实标注，不装作全知。

### R5 让句子有节奏

- 长短句交替。相邻句子不要同一开头（"同时……同时……""此外……此外……"）。
- 列表项数量由内容决定：2 项就 2 项，5 项就 5 项，不凑三件套。
- 段落长度自然变化，不要求每个章节都写成"总-分-总"。

### R6 平实用词

- 动词优先："配置好了"而不是"完成了配置的操作"。
- 砍掉不承载信息的形容词：强大的、灵活的、优雅的、无缝的、全面的、卓越的。
- 技术名词保留英文（commit、debug、Docker），不硬翻。

## 二、禁止模式（黑名单）

以下是 AI 高频套路，成文后全文搜索这些词句，出现即改。

### P1 铺垫代替陈述

- "不是 X，而是 Y"/"不仅仅是……更是……"句式 → 直接说它是什么、做到了什么。
- "让我们一起来探索/深入了解……" → 删掉，直接进入内容。
- 每段结尾补一句升华/金句 → 删掉，只保留真正有信息量的。
- 段落开头"值得注意的是/需要指出的是" → 直接写要说的事。

### P2 机械节奏

- 凡列举必三项 → 按内容实际数量。
- 连续排比（"它是……它是……它是……"）→ 拆成不同结构的句子。
- 破折号、分号当万能连接词 → 用句号断开，或改成"因为/所以"。
- 每个标题下先来一段"本节将介绍……"的预告 → 删掉预告，直接写内容。

### P3 拔高与空洞

- 高频空洞词：关键、至关重要、不可或缺、显著、极大、深远、赋能、闭环、生态 → 换成具体事实。
- "标志着……新阶段""为……奠定了坚实基础" → 写出实际影响：影响了什么、影响了谁。
- 无来源的权威背书："专家认为""研究表明""众所周知" → 给出具体来源，或删掉。
- 无意义的模糊限定："在某种程度上""某种意义上" → 删除，除非确实需要保留不确定性。

### P4 装饰性排版

- 加粗当装饰、满篇加粗 → 只加粗真正需要强调的，单段不超过一处。
- 标题带 emoji 或装饰符号 → 标题用纯文字（`readme-template.md` 要求的 `📋 目录` 为唯一例外）。
- 标题层级超过三层（出现 `####` 以下）→ 重组内容层级。
- "**词：** 说明"式列表项 → 说明本身能读通时改写为正常句子。

### P5 聊天残留

- "好问题！""希望本文对你有帮助！""以上就是全部内容" → 全部删除。
- 结尾"综上所述/总而言之"复述开头 → 删掉；需要收尾就写下一步动作或验证方法。
- "如有疑问，欢迎交流"式空话 → 删除，除非文档里确有明确的反馈渠道。

### P6 编造与空壳（红线）

- 占位符内容（xxx、TODO、待补充、示例值）→ 没有内容就整节删除，不留空壳。
- 虚构引用、链接、数字 → 只写验证过的事实，拿不准就不写。
- 把推测写成断言（"这一定是因为……"）→ 写明依据，或标注为待验证。

## 三、结构检查（交付前逐项自查）

- [ ] 第一段回答了"读者读完能获得什么"？
- [ ] 技术类文档的每个主要章节都有代码块或终端命令，示例含预期输出？
- [ ] 版本号、路径、参数都是项目真实值？全文搜一遍 xxx / TODO / foo / 待补充？
- [ ] 操作步骤完整：前提条件 → 命令 → 预期结果，读者不用猜？
- [ ] 已知的坑、限制、适用范围写了吗？
- [ ] 列表数量都符合内容实际？没有连续多个列表都是三项？
- [ ] 黑名单词句（第二节）搜过一遍？
- [ ] 删掉开头的铺垫句与结尾的总结句后信息有损失吗？没损失说明删对了？
- [ ] 朗读一遍：像同事在座位上给你讲，还是像产品宣传页？

## 四、按文档类型的场景要求

### 技术指南 / 教程（docs/guide/）

- 开头给收益：读完你能做到什么，附带前提与需要的时间/环境。
- 每个主要部分至少一个可执行示例（命令、代码、配置），并给出预期输出。
- 关键步骤写明失败时怎么办：常见报错与排查入口。
- 结尾不用总结，用验证清单：做哪几个动作可以确认整条链路可用。

### README

- 骨架与章节顺序遵循 `readme-template.md`，本文件约束语气。
- 一句话描述写清"做什么 + 给谁用"；快速开始部分删掉解释性形容词，只留可复制的命令。
- 常见问题只收录真实遇到过的问题，问题标题用真实报错文本。

### 架构 / 决策文档（docs/architecture/）

- 写"为什么"和"代价"，不写技术概念教科书。
- 每个决策四件事：选了什么、为什么选、否决了什么、什么条件变化时该重新考虑。
- 禁止自我表扬（"本架构非常健壮""具备良好的可扩展性"），用事实替代：并发量、数据量、实测延迟。

### 排错指南 / FAQ

- 标题用真实报错文本或用户原话，不用"某功能异常"这类抽象表述。
- 三段式：症状（报错原文）→ 原因 → 解决（命令或配置改动）。
- 保留试错过程（"先试了 X 不行，因为……"），这是最贴近真人的部分。

### CHANGELOG

- 格式遵循 `changelog-template.md`。条目写"改了什么、影响谁"，不写"优化了体验"这类无法验证的空话。
- BREAKING 条目必须写迁移动作：调用方需要改哪一行。
