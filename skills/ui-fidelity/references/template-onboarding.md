# 新模板接入流程（Onboarding）

> 目标：把任意一个陌生的开源前端模板，变成一份可执行的 UI 基线。
> 触发：仓库根没有 `docs/ui-baseline.md`，或要接入一个没用过的模板。
> 存放位置：固定在**仓库根**的 `docs/` 下。前后端分离时前端代码在子目录，基线文件仍放仓库根，不跟着进前端项目。
> 原则：**只写从代码里读到的事实**，不写官网宣传语，不写训练记忆里的印象。

## 零、先在项目里声明身份

本技能靠 description 语义匹配触发。模型在新会话里不知道“这个项目是 vue-pure-admin 二开”，就不会主动加载它，表现为“要用户点名才用”。

解法是在**项目根**建 `AGENTS.md`，把项目身份写成随会话启动注入的规则（Qoder 已原生兼容 AGENTS.md，Claude Code、Codex、Cursor 等同样读取）：

```markdown
# 项目约定

## 前端
- 前端代码位于 `frontend/`，基于 vue-pure-admin 二开。
- 改动任何前端页面、组件、样式前，必须先加载 `ui-fidelity` 技能，并读取 `docs/ui-baseline.md`。
- 颜色 token、组件、图标只能取自基线白名单；白名单没有的停下询问，不要自造。
```

这几行在会话开始时就进入上下文，不依赖触发匹配，比 description 可靠。IDE 不读 AGENTS.md 时，写进各自的规则目录（如项目内 `.qoder/rules/`、`.codebuddy/rules/`）。

## 一、先判形态

| 形态 | 判定依据 | 后续必读 |
| ---- | -------- | -------- |
| PC 中后台 | 有侧边栏布局壳、表格、分页器 | 本文件 + `baseline-template.md` |
| 移动端（uni-app / 小程序 / H5） | 有 tabBar、rpx、下拉刷新、安全区 | 本文件 + `mobile.md` + `baseline-template.md` |

## 二、侦察顺序（按顺序读，不要跳步）

**0. 定位仓库根与前端代码目录**

有 git 时用 `git rev-parse --show-toplevel` 确认仓库根；前端代码可能在 `frontend/`、`web/`、`apps/admin/` 等子目录。记下这层相对关系并填入基线第 1 节，后续所有基准页路径都相对该目录书写。

**1. 读 `package.json`**

确认四件事：Vue 版本、UI 组件库及版本、CSS 方案（SCSS / Tailwind / UnoCSS / Less）、图标方案。
这一步决定后续所有语法判断，例如 Tailwind 4 的 `w-45!` 与 Tailwind 3 的 `!w-45` 完全不同。

**2. 找全局样式入口**

常见位置：`src/style/`、`src/styles/`、`src/assets/styles/`、`app.scss`、`main.ts` 的 import 语句。
记录：主题变量文件、UI 库样式覆盖文件、reset 文件。这三类文件就是「禁止 AI 改动」的清单。

**3. 读主题变量文件**

找出颜色 token 全集，以及暗色主题的实现方式（`.dark` class / `html[data-theme]` / media query）。
颜色可能分散在两处：CSS 变量文件与 SCSS 变量文件，两边都要看。

**4. 找封装组件目录**

常见位置：`src/components/`、`src/components/Re*`、`@/components`。
重点找四类封装：表格、表格工具栏、弹窗表单、图标渲染。它们是「禁止用裸 UI 库组件替代」的对象。

**5. 挑基准页（最关键的一步）**

优先选系统管理类页面（用户、部门、角色），因为它们通常写得最规范。
判定标准：同时包含搜索、表格、分页、工具栏按钮、行操作五要素。
至少挑 1 个列表页；有表单页和详情页时各挑 1 个。

**6. 确认 lint 命令**

读 `package.json` 的 scripts，记录 lint 与 typecheck 命令，注意是否包含 stylelint、是否有 Tailwind class 校验插件。

## 三、先出草稿，不要直接写页面

侦察完成后按下列格式输出，等用户确认再落盘：

```
已侦察到的事实：
- 技术栈：<Vue 版本 / UI 库及版本 / CSS 方案 / 图标方案>
- 全局样式入口：<文件列表>
- 颜色 token：<数量与来源文件>
- 封装组件：<表格 / 工具栏 / 弹窗 / 图标 分别是什么>
- 建议基准页：<路径 + 选它的理由>
需要你确认：
1. 基准页是否合适？我还看到 A、B 两个页面，是否一并纳入？
2. 颜色 token 只有 N 个，是否还有其他来源？
3. 禁止清单除通用项外，还有哪些项目特有红线？
```

## 四、判定基线够不够用

三个自问，任一条答不上就是没填完：

1. 随便指一个新页面需求，能不能立刻说出「抄哪个文件」？
2. 随便指一个颜色，能不能说出「用哪个 token」？
3. 随便指一个表格，能不能说出「用哪个组件」？

## 五、禁止事项

- 禁止按模板官网的特性介绍填写基线——宣传语描述的是能力，不是约束。
- 禁止凭训练数据记忆填写 token 名、组件名、导入路径，必须从代码里读到。
- 禁止把「网上教程的常见写法」当成项目事实。
- 侦察结果拿不准时列出来问用户，不要猜、不要留空让 AI 自由发挥。

## 六、什么时候把基线沉淀成实例文件

同一模板被第 3 个项目复用，或该模板有强独特约定（如配置驱动的表格组件、schema 驱动的搜索表单）时，才值得在 `references/` 下新增一份 `<模板名>.md`。
只接入一次的项目不必沉淀——模板细节会随版本失效，提前写等于制造过期文档。
