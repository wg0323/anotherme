# 开源模板二次开发 · 界面保真规范

目标：新增的每个页面，放在模板原有页面旁边看不出差别。

## 一、核心铁律（最高优先级）

1. **先读后写**：动手前先读**仓库根**的 `docs/ui-baseline.md`（前后端分离时不在前端子目录里另建 docs）。文件不存在时，先按 `references/template-onboarding.md` 侦察模板并输出基线草稿供用户确认；移动端项目另读 `references/mobile.md`。未完成基线不得生成页面代码。
2. **抄而不创**：新页面从最接近的现有页面复制起手，只替换字段、接口、列定义与文案，不改动布局骨架与样式写法。
3. **只用白名单资产**：颜色、间距、圆角、组件、图标、布局工具类只能取自基线文件的白名单；白名单里没有的一律视为违规。
4. **缺失即停**：找不到对应组件或样式时立即停下询问用户，禁止自行新建组件、自行引入 UI 库、自行发明设计令牌。
5. **只改需求涉及的行**：不重构无关样式、不顺手“优化”周边代码、不批量替换 class。
6. **不覆盖全局**：样式调整只写在当前组件 `<style scoped>` 内；修改全局样式或 `.el-*` 内部类必须提前获得用户同意。

## 二、生成前必须输出对齐声明

写代码之前先输出下面三行。读不到真实内容说明基线不全，停止并询问用户：

```
参照基准：<基准页文件路径>
将复用：<组件名 / 布局工具类 / 颜色 token 清单>
将新增：<无 | 具体新增项及理由，需用户确认>
```

## 三、高频违和点速查

| 违和来源 | 典型表现 | 正确做法 |
| -------- | -------- | -------- |
| 颜色 | 直接写 `#409eff`、`bg-white`、`text-gray-500` | 用项目颜色 token，暗色主题才会跟着变 |
| 原子类版本 | 沿用训练数据里的旧语法（如 Tailwind v3 的 `!w-4`） | 以项目实际版本为准，先看现有页面怎么写 |
| 组件绕过 | 用裸 `el-table` 或原生 `div` 拼装，替代模板已封装的业务组件 | 复用封装组件，保持工具栏、分页、列设置一致 |
| 图标 | 另引图标库或直接引入图标组件 | 走模板统一的图标渲染方式与图标集 |
| 间距 | 自选 `p-4`、`mt-3` 等散值 | 沿用基准页的间距与卡片包裹方式 |
| 样式覆盖 | 全局改 `.el-xxx`、`!important` 堆叠 | scoped + `:deep()`，不改组件内部结构 |

## 四、交付前自检

1. 逐项过 `references/review-checklist.md`；
2. 输出差异说明：`与基准页的结构差异：<无 / 具体差异及原因>`；
3. 运行项目 lint（如 `pnpm lint`），有报错先修完再交付。

## 五、详细规范（按场景按需读取）

| 场景 | 参考文件 |
| ---- | -------- |
| 首次接入一个没用过的模板 / 仓库内还没有基线文件 | `references/template-onboarding.md` |
| 需要填写或更新项目基线文件 | `references/baseline-template.md` |
| 目标项目是 vue-pure-admin（含真实 token、页面骨架、正反例） | `references/vue-pure-admin.md` |
| 目标项目是移动端（uni-app / 小程序 / H5） | `references/mobile.md` |
| 代码写完后逐项自检 | `references/review-checklist.md` |

## 六、与其他技能的分工

同时命中多个技能时按维度取规则，不要互相覆盖：

| 维度 | 以谁为准 |
| ---- | -------- |
| 视觉一致、骨架对齐、组件复用、禁止项 | 本技能 |
| uni-app / 小程序的语法与工程结构 | `uniapp-spec` / `wx-miniapp-spec` |
| 后端接口与工程分层 | `springboot-spec` |
| 提交信息与分支 | `gitflow` |
