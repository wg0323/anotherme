# 回归测试范围决策

项目多轮迭代后，回归测试的难点不是"怎么测"，而是"这一轮该测哪些"。本文件给出可复算的决策规则：既不默认全量，也不只测改动点。

## 前提：先量全量成本

选择性测试本身有推导与维护成本。先用一次实测数据判断要不要引入它。

| 全量耗时（编译 + 单测 + 冒烟） | 策略 | 说明 |
| --- | --- | --- |
| ≤ 5 分钟 | **每次全量** | 不引入任何选择机制。推导成本高于省下的时间 |
| 5～30 分钟 | 按下面的分级 + 影响面选择 | 大多数个人或小团队项目落此档 |
| > 30 分钟 | 分级选择 + 自动化映射 | 才值得把影响面推导脚本化，并考虑并行执行 |

判定依据必须是一次真实测量的耗时，不接受"感觉挺慢"。测量时区分冷启动（含编译、依赖下载）与热启动。

## 变更分级

| 级别 | 判定条件（任一命中） | 必跑范围 | 时间预算 |
| --- | --- | --- | --- |
| L0 无行为变更 | 仅文档、注释、格式、空白 | 编译通过 | 1 分钟内 |
| L1 局部行为 | 单模块内业务逻辑、单接口实现、单页面样式 | 该模块单测 + 该模块所在主流程冒烟 | 分钟级 |
| L2 跨模块 / 契约 / 结构 | 公共组件、工具类、异常与日志处理、拦截器与过滤器、鉴权中间件、DB 表结构与索引、API 出入参、MQ 消息体与路由键、配置项、依赖版本 | 全量冒烟 + 受影响模块单测 + 契约相关集成测试 | 十几分钟 |
| L3 核心链路 / 发版 | 登录鉴权、订单支付、消息可靠投递与消费、事务与幂等、发版或里程碑 | 全量回归（含冒烟） | 半小时级 |

定级规则：

- **共享代码按最大影响面定级**。改 3 行工具类、改 1 个配置 key、改 1 个 DTO，一律 L2，不按改动行数定级。
- **一处 L2 + 一处 L1 时取高**，不叠加也不降级。
- 一次改动跨多个级别时，按最高级别执行，不需要为每级各跑一遍。

## 影响面推导：三张图

逐条走完再决定范围。任何一条走不通，转下面的 fail-safe。

### 代码图

```bat
:: 本次改动涉及的文件（含工作区未提交部分）
git status --porcelain
git diff --name-only HEAD

:: 改动的符号被谁引用（优先用 LSP 的 findReferences，退化为文本检索）
findstr /s /n "SymbolName" src\*.java
```

- 改动类 → 同包同名 `*Test`；找不到对应测试即为覆盖缺口。
- 改动符号 → 调用方（引用方）→ 调用方的测试类。
- 前端改动 → 通过 import 关系向上找页面与路由入口。

### 数据图

改到的表、字段、索引、枚举、字典值，沿"谁在用"向下追：

```
表/字段 → Mapper 与 SQL（含 XML 动态片段） → Service → Controller/接口 → 页面
```

- 改了字段类型、长度、可空性、默认值：所有读写该字段的路径都受影响，不止增删改查那一处。
- 改了枚举或字典值：所有按该值分支的逻辑都要看，包括历史数据的兼容性。

### 契约图

- API 路径、入参、出参、错误码 → 前端调用点、其他调用方。
- MQ 消息体、routing key、交换机与队列声明 → 生产端与消费端，两边都算受影响。
- 配置项 key 与默认值 → 所有读取该配置的分支，以及部署环境里的实际取值。

## fail-safe：推导不出就升级

出现下列任一情况，跳过推导，直接按 L2/L3 跑全量：

- 找不到对应测试，或测试明显未覆盖改动的分支。
- 改动落在动态执行路径上：MyBatis XML 拼 SQL、反射、SpEL、注解驱动、配置开关分支。
- 改动涉及框架或依赖版本、序列化方式、时区、字符集、编码、拦截器链顺序。
- 改动涉及跨层约定：事务边界、异常映射、日志格式、鉴权上下文传递。
- 你对影响面的判断说不清，只能给出"应该没事"。

原则：**选择机制只允许"多跑"，不允许"少跑"**。任何模糊点都向全量方向倒。这与微软 Azure DevOps 测试影响分析的官方设计一致——对无法解析的变更回退到运行全部测试。

## 冒烟集

冒烟集是一份版本化的清单，不是每轮临时挑。构成规则与模板见 `smoke-checklist-template.md`，此处只定约束：

- 5±2 条核心用户旅程，覆盖：进门（登录/鉴权）→ 主干业务闭环（写入后查询可见）→ 关键副作用（落库、消息投递与消费）。
- 每条必须可自动化执行，有明确入口、预期产物、成功判据、耗时上限。
- 除 L0 外每轮必跑，这是固定成本，不参与取舍。
- 新增核心功能同步补一条；只增不减。

## 周期性全量兜底

增量选择的漏检风险会随轮次累积，必须有固定出口。满足任一条件即跑全量：

- 距上次"全量全绿"≥ 2 周，或累计 ≥ 10 次改动。
- 本轮含 L3 变更。
- 子集或冒烟刚失败并已完成修复（修复本身是高风险变更）。
- 依赖大版本升级、DB 结构变更、中间件或配置变更。
- 发版前。

## 缺陷回流

任何**事后才发现**的回归（线上、手工发现、下一轮迭代才暴露），在 24 小时内完成两件事：

1. 补一条冒烟用例（主流程类问题）或一条单测（逻辑分支类问题）。
2. 记入冒烟清单或测试清单，注明来源。

原则：**同一个回归不允许逃逸第二次**。测试集腐烂的根因通常不是覆盖不够，而是漏了之后没有沉淀。

## 一轮迭代的执行流程

| 步骤 | 动作 | 验证点 |
| --- | --- | --- |
| 1 | 记录基线：当前 commit、上次全量全绿的 commit | 两个 hash 明确，diff 可复算 |
| 2 | 列出变更面：按代码 / 配置 / SQL / 前端 / 文档分类 | 分类清单无"其他"项 |
| 3 | 定级（L0～L3），按三张图列影响集 | 影响集有清单；推导不出的项已标为全量 |
| 4 | 执行：编译 → 单测子集 → 冒烟 → 受影响接口联调 | 每步先定义预期产物与判据，再设超时 |
| 5 | 判读结果 | 按下方红线判定，不看单一退出码 |
| 6 | 收尾：终止本次启动的进程，清理临时脚本与日志 | 端口释放，无残留 |
| 7 | 留痕并判断是否触发全量 | "测了什么、没测什么"可复查 |

执行过程本身的纪律（预估耗时、止损、读现场、清理）见 `expectation-baseline.md`、`hang-diagnosis.md`、`cleanup.md`。

## 不算"测过"的红线

- 编译成功：只证明能编译。
- 启动成功：只证明能启动。
- 退出码为 0 但 `Tests run: 0`、全部 skip、用例被禁用。
- 手工点了一下"看着正常"。
- 子集通过，但没记录跑了哪些测试：下轮无法复查，也无法判断漏检。

## 选型有效性审计

每 10 次改动做一次，成本约半小时，用于验证"选择机制本身没坏"：

1. 选一个典型提交，同一份代码先跑子集（T1），再跑全量（T2）。
2. 对比两次结果：T1 通过而 T2 失败 → 存在漏选，立刻修映射规则或补冒烟；两者失败用例不一致 → 存在环境或顺序依赖问题。
3. 记录三个数：逃逸缺陷数、冒烟总耗时、子集总耗时。趋势恶化就升级策略（缩短全量周期或直接回到每次全量）。

这套对比法是微软 TIA 官方文档给出的验证手段，用于人工核对所选测试是否恰当。

## 业界来源与取舍

| 来源 | 核心做法 | 采纳情况 |
| --- | --- | --- |
| Google（TAP / Taming Google-Scale Continuous Testing） | 按构建依赖图为每次提交选子集，postsubmit 跑全量 | 采纳"子集 + 周期全量"骨架，不引入其构建图工程 |
| Microsoft Azure DevOps 测试影响分析（官方文档） | 动态覆盖率建立"测试 ↔ 源码"映射；无法解析则回退全量；始终包含新增测试与上轮失败测试；支持配置周期全量 | 采纳全部安全机制；映射用"代码引用 + 数据链路 + 契约链路"近似实现 |
| Meta 预测性测试选择 | 机器学习预测每个测试失败概率，只跑约三分之一仍捕获绝大部分回归 | 不采纳，列为演进预案；触发条件为测试达千级且全量 > 30 分钟 |
| ISTQB 风险驱动测试 | 按风险优先级选择回归范围，优先测试高风险与修改局部 | 采纳，落地为变更分级 L0～L3 |
| Paul Hammant《The Rise of Test Impact Analysis》 | 若测试足够快就每次全跑，否则在成本与价值间平衡；覆盖率工具可用于自建映射 | 采纳其成本优先判断，作为本文件的"前提"一节 |

## 收益与成本裁决

以"每次全量"为基线，逐项判断引入的复杂度是否值得：

| 设计点 | 相对基线 | 收益 | 成立阈值 | 成本 | 裁决 |
| --- | --- | --- | --- | --- | --- |
| 分级 + 影响子集 | 向上加码 | 单轮耗时从全量降到子集 | 全量 > 5 分钟 | 每轮 3～5 分钟推导 | 条件采纳，先实测再定 |
| 固定冒烟集 | 向上加码 | 每轮低成本兜住主流程 | 恒成立 | 首次约 1 小时建立，之后每轮 5 分钟 | 采纳 |
| 周期全量 | 向上加码 | 抵消增量选择的累积漏检 | 恒成立 | 每 2 周一次全量 | 采纳 |
| 覆盖率驱动自动映射 | 重度加码 | 省掉手工推导 | 全量 > 30 分钟且测试数百个 | 脚本与映射维护 | 降级为演进预案 |
| 机器学习预测选择 | 重度加码 | 进一步减少测试量 | 测试达千级且有历史数据 | 训练数据与模型维护 | 当前禁止采纳 |
