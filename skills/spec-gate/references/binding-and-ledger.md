# 技能绑定与规范偏差台账

## 一、阶段划分

绑定按“产出对象类型”触发，不按“任务步骤”触发。下面是常见工程的阶段切分，实际项目按自己的分层裁剪，但**每次切换都要重新绑定**。

| 栈 | 阶段序列 | 切换信号 |
| --- | --- | --- |
| 后端（SpringBoot） | 依赖与配置 → 数据层（entity / mapper / db 脚本） → 服务层 → 接口层（controller / dto / vo） → 测试 | 开始写新一层的第一个文件 |
| 前端（Vue 后台） | 路由与骨架 → 页面 → 组件 → 接口联调 → 构建 | 开始写新一类的文件 |
| 移动端（uni-app / 小程序） | 页面骨架 → 组件 → 请求封装 → 跨端适配 | 同上 |
| 跨端整体 | 后端 → 前端 → 联调 | 换端 |

阶段切换只看一件事：**接下来要产出的对象类型，和上一阶段是否相同**。相同则沿用，不同则重出绑定表。

## 二、技能绑定表

```text
【技能绑定】阶段：服务层（第 2 次）
| 产出对象 | 必载技能 | 本次要遵守的条款 |
| service/OrderService.java | springboot-spec, java-spec | SB-8, SB-1, SB-4 |
| service/impl/OrderServiceImpl.java | springboot-spec, java-spec | SB-8, SB-1, SB-2, SB-4 |
```

要求：

- 「必载技能」写技能名，「本次要遵守的条款」写条款 ID，不写“遵循规范”这种废话
- 条款 ID 取各技能正文的稳定编号（如 `springboot-spec` 的 `SB-N`）
- 技能正文没有编号时，引用“章节名 + 该章节里与本次对象相关的条目”，并顺手建议给该技能补编号

## 三、规范偏差台账

```text
【规范台账】模块：订单
| 条款 | 判定 | 依据 |
| SB-1 | 遵守 | OrderServiceImpl:23 @RequiredArgsConstructor |
| SB-8 | 遵守 | service/OrderService.java + service/impl/OrderServiceImpl.java |
| SB-12 | 不适用 | 本次为存量工程增量，未新建工程骨架，触发条件不成立 |
| SB-15 | 偏差·已裁决 | 计划要求 Flyway；用户裁决按计划执行，风险：启动期自动改库 |
```

规则：

- 一行一条条款，按绑定表里出现过的条款逐条收口，不合并成“其余均符合”
- 「不适用」的判据必须指向触发条件，不能指向任务属性
- 「偏差」必须带裁决状态：`待裁决` / `已裁决（用户原话要点）`
- 交付时台账里不允许出现 `待裁决`

## 四、计划文档阶段的集成

计划文档是冲突的高发地：它比技能更具体，容易覆盖技能。因此在**写计划时**就完成一半工作：

1. 计划文档必须包含「技能绑定与冲突预案」一节，列出本计划会产出哪些对象类型、各自必载的技能
2. 逐条比对计划要求与技能铁律，任何冲突在计划评审阶段就上报，不留到实现
3. 计划被用户确认后进入权威层级第 1 档，但它**仍然不能覆盖技能铁律**——冲突必须重新上报

检查方法：把计划里每一个“必须 / 禁止”与技能铁律做交叉表。计划中出现技能明令禁止的技术（如 Flyway），必须当场标注为冲突。

## 五、不需要重出绑定表的情形

同一阶段内修 bug、改文案、调参数、补齐上一轮台账里的偏差项，不需要重出绑定表。

注意：不重出不等于不核对。若过程中改动了对象类型（比如修 service 时顺手改了 mapper），就要补一次绑定与台账。
