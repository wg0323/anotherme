# 规范遵循度门禁

已有的规范技能解决“条款怎么写”，`code-gate` 解决“代码可不可信”，中间这一层没人负责：**技能加载了，到底有没有照着执行**。本技能只做一件事——把“应该遵守”变成每次都必须提交的工件，让跳过、降级、自裁都留下可检查的痕迹。

## 核心铁律

1. **绑定表与台账是交付物，不是自检记录**。未输出即视为未执行；写了但没核对，等同没写。
2. **判“不适用”必须给触发条件不成立的事实**。“存量工程”“已批准的设计”“任务很小”“只是改几行”一律不构成理由。
3. **条款冲突一律上报**。用户指令、计划文档、技能铁律、项目现状四方任意两者冲突，都走 `common_rule` 的冲突停机格式，禁止自行选择一方。
4. **阶段切换必须重新绑定**。不得复用开场那张表；切换信号是“接下来要产出的对象类型变了”，不是“用户提了新需求”。
5. **计划文档是输入不是规范**。计划与技能冲突在计划阶段就要上报，不能等到实现时才发现。计划本身应包含「技能绑定与冲突预案」一节。
6. **本技能只管“是否遵守”，不管“条款对不对”**。发现条款本身有问题（歧义、过时、互相矛盾），记录并提给用户修订，不擅自绕过。

## 三态判定

台账每行只能落在三态之一，不允许留空：

| 判定 | 必须给 |
| --- | --- |
| 遵守 | 文件路径 + 符号位置（类 / 方法 / 配置项） |
| 不适用 | 触发条件不成立的事实（如“本次未新增 pom，SB-11 的配置触发条件不成立”） |
| 偏差 | 理由 + 影响 + 用户裁决记录；未裁决者不得交付 |

## 与相邻技能的分工

| 问题 | 归属 |
| --- | --- |
| 条款内容是什么、怎么写才对 | 各规范技能（`java-spec`、`springboot-spec`、`db-spec` 等） |
| 本次改动命中了哪些条款、有没有执行 | 本技能 |
| 代码是否可信、测试是否有效 | `code-gate` |
| 测试跑多大范围、怎么跑 | `test-execution` |
