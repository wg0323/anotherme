# 方案收益与复杂度权衡分析

> 本文件是 `solution-design` 技能"方案收益评估（强制）"章节的操作细则。
> 核心命题：**技术可行 ≠ 值得实施**。一个方案能被写出来、能跑通，不代表它相对业界标准基线有正收益。
> 基线 = 业界标准方案（经搜索锚定的、真实生产环境广泛使用的做法）。**低于基线的简化**不归本文件管，须按 SKILL.md"本地资源受限时的替代方案"的降级路径处理；本文件只裁决**高于基线的加码**。

---

## 一、典型失败模式

| 失败模式 | 表现 | 后果 |
|----------|------|------|
| **零收益复杂度** | 方案在当前量级与部署形态下，相对业界标准基线无任何指标增量 | 代码分支变多、测试面变大、排障变难，净收益为负 |
| **阈值错配** | 优化只在极端量级生效，用户业务量级远低于该阈值 | 为不存在的问题付真实成本 |
| **自相矛盾** | 为修复方案副作用引入的约束，恰好抵消其声称的收益 | 收益恒为 0，复杂度全额保留 |
| **形态错配** | 在单机/单实例形态下套用只为水平扩展设计的方案 | 瓶颈未变（仍是同一进程/同一线程），收益为 0 |
| **模糊话术替代论证** | 用"提升性能""更健壮""为将来做准备"结尾 | 用户无法判断是否该采纳 |

## 二、收益评估五步法

### Step 1 立基线（Baseline = 业界标准方案）

先回答：**同类需求在真实生产环境/主流开源项目中，默认是怎么做的？** 基线是经搜索锚定的业界标准方案（它通常也就是满足需求的最简正确实现），不是"我能想到的最省事写法"。

写基线时要写清：数据结构、关键操作、原子性如何保证、落库方式、预估能支撑的量级。

> 收益 = 方案指标 − 基线指标。**没有基线，就没有收益可言。**
> 注意方向：本文件只论证"在基线之上加码"的收益；**低于基线的简化**（如业界用 Redis 你用 MySQL）不适用收益论证豁免——它必须走 SKILL.md 的资源受限降级路径，证明业界方案在本地确实跑不了。

### Step 2 定位收益类型

收益必须落到下表某一格，并给出数字或数量级：

| 类别 | 指标 | 度量方式 |
|------|------|----------|
| 性能 | QPS/TPS、P99/P999 延迟、批处理耗时 | 压测（`redis-benchmark`、`wrk`、JMH）、APM |
| 资源 | 内存占用、连接数、CPU 核数、磁盘 IOPS、存储量 | 监控指标、`INFO`/`SHOW STATUS` |
| 可用性 | 故障影响面（全量/分片）、RTO、RPO、单点数量 | 故障演练、架构推演 |
| 成本 | 机器数、人力工时、运维巡检项数量、第三方费用 | 直接估算 |
| 正确性 | 数据不一致窗口、超卖/重复概率 | 逻辑推演 + 测试 |

**若一个方案说不出它改善上表哪一格，它的收益就是 0。**

### Step 3 找出成立条件（阈值）

任何优化都有生效阈值。必须回答：

- 在什么**数据量 / 并发量级**下开始生效？
- 在什么**部署形态**下才生效？（单机 vs 集群、单实例 vs 多实例、单库 vs 分库）
- 低于阈值时收益是多少？（绝大多数情况是 **0**，而不是"小一点的正数"）
- 用户的**实际量级**离阈值有多远？（差一个数量级 = 用不上）

拿不到准确阈值时：查官方基准文档、查参考开源项目的压测报告、或本地压测；仍拿不到就标注"**未验证推测**"并给出验证方法。

### Step 4 列全成本

| 成本项 | 具体问什么 |
|--------|-----------|
| 代码复杂度 | 新增多少类/方法/分支？是否引入重试、探测、聚合、补偿逻辑？ |
| 测试成本 | 新增多少测试用例？边界条件是否显著变多（如分片不均、部分失败）？ |
| 运维成本 | 新增多少监控项？出问题时排障要看几个地方？ |
| 依赖成本 | 是否引入新中间件/新客户端？版本兼容与升级负担？ |
| 一致性风险 | 是否把原本原子的操作拆成多步？失败中间态如何收敛？ |
| 认知成本 | 新人理解这段逻辑需要多久？是否有反直觉设计？ |

### Step 5 裁决

| 裁决 | 判定条件 | 处理 |
|------|----------|------|
| **采纳** | 净收益为正且阈值在用户量级内可达 | 进入实施范围，写明量化预期 |
| **降级为演进预案** | 收益为 0 / 阈值远超当前量级 / 无法验证 | **不进实施范围**，写清触发阈值 + 迁移路径 |
| **禁止采纳** | 净收益为负，或方案自相矛盾 | 明确告知用户这是过度设计及原因 |

**裁决表模板（复制到方案中使用）：**

```markdown
| 设计点 | 基线做法 | 本方案做法 | 量化增量 | 成立阈值 | 成本 | 裁决 |
|--------|----------|------------|----------|----------|------|------|
|        |          |            |          |          |      | 采纳 / 演进预案 / 禁止采纳 |
```

## 三、常见优化的生效阈值参考

> 下表为**数量级参考**，用于快速识别"阈值错配"，不可直接当作结论引用；正式方案中须以实测或官方基准校正，并注明来源。

| 优化手段 | 收益开始生效的条件 | 低于阈值时的收益 | 典型副作用 |
|----------|--------------------|------------------|------------|
| Redis 单 key 拆分为多分片 | 单 key 操作量逼近**单节点单线程处理上限**，且部署在 Cluster 多节点上 | **0**（同一节点内拆分不增加吞吐） | 需探测/聚合逻辑；跨槽失去原子性；假失败 |
| 分库分表 | 单表数据量达千万级以上或单库写入达瓶颈 | 0 | 跨库事务、跨库分页/聚合、扩容重分片 |
| 读写分离 | 读 QPS 显著超出单实例承载，且业务可容忍主从延迟 | 0 | 读到旧数据、延迟判定、故障切换复杂化 |
| 多级缓存（本地 + 分布式） | 存在真实热点且分布式缓存往返成为可测瓶颈 | ≈0 | 本地缓存一致性、失效广播、内存占用 |
| MQ 异步削峰 | 存在**瞬时峰值 >> 均值**的流量，且下游处理慢于上游写入 | 0（平稳流量下只是多一跳延迟） | 消息可靠性、顺序性、幂等、堆积监控 |
| 服务拆分 / 微服务 | 团队规模与发布频率已到单体互相阻塞的程度 | **负**（小团队） | 分布式事务、链路追踪、部署与运维成本 |
| 引入 ES 做检索 | 存在多字段组合查询/全文检索，DB 索引已无法覆盖 | 0 | 数据同步、双写一致性、集群运维 |

## 四、完整反例：抢红包的 Redis 分片方案

### 4.1 需求

实现"发红包 / 抢红包"：一个红包有固定总金额与份数，多人并发抢，要求不超发、不少发、抢完即止。

### 4.2 基线（业界标准方案）

- 一个红包对应**一个 Redis key**（或 hash），存剩余金额与剩余份数。
- 抢红包用**一段 Lua 脚本**完成"判断余量 → 计算本次金额 → 扣减"，Redis 单线程执行保证原子性，天然不超发。
- 抢到后异步落库，退款时按 key 余量结算。
- 承载能力：单节点 Redis 上此类 Lua 操作的量级通常在**万级 QPS 以上**（具体值取决于脚本复杂度与 value 大小，需 `redis-benchmark` 实测）。

对照真实业务量级：一个 500 人群抢红包，峰值并发是**几百到几千 QPS、持续不到 1 秒**。基线余量充足。

### 4.3 待评估方案

把一个红包拆成 N 个分片 key（`rp:{id}:slot:0..N-1`），金额预拆分到各分片；抢红包时随机选一个分片扣减，命中空分片则探测其他分片。理由："分散热点，支持水平扩展"。

### 4.4 收益分析

**形态一：单机 Redis（非集群）**

| 项 | 结论 |
|----|------|
| 吞吐增量 | **0**。Redis 命令由单线程执行，瓶颈是单核 CPU 与网络。把 1 个 key 拆成 N 个 key，它们仍在同一进程、同一线程排队，总吞吐不变 |
| 实际吞吐 | **下降**。原本 1 次命令完成，现在命中空分片需重试探测，命令数变为 1~N |
| 可用性增量 | **0**。仍在同一节点，节点挂则全挂 |
| 正确性 | **变差**。分片预拆分导致金额分布不均，出现"某分片已空但整体仍有余款"的假失败，需补偿逻辑 |

→ 收益 0，成本为正，**净收益为负**。

**形态二：Redis Cluster**

| 项 | 结论 |
|----|------|
| 理论收益 | 分片 key 按 CRC16 落到不同节点，理论上可把热点分散到多节点 |
| 生效阈值 | 单个红包的并发 QPS 必须逼近**单节点单 key 处理上限**（万级 QPS 以上）。真实业务（群红包、活动红包）几乎不可能对**单个红包**产生这种量级的持续压力 |
| 自相矛盾点 | Cluster 下 Lua 脚本操作多 key 要求各 key 位于**同一 slot**，否则报错。要保原子性就得加 hash tag（如 `rp:{id}:slot:0`），而 hash tag 会让**所有分片落回同一节点**——"分散热点"的收益**恒为 0**，只剩复杂度。若不加 hash tag，则跨节点多步扣减失去原子性，引入超发风险——收益转为**负** |
| 延迟 | 变差。分片探测带来多次跨节点往返，RTT 叠加，P99 上升 |

→ 阈值远超真实业务量级；且无论如何选择原子性策略，收益都被抵消。**净收益 ≤ 0**。

### 4.5 成本分析

新增分片路由、空分片探测与重试、余量聚合查询、退款时的多分片结算、分片金额预拆分算法；测试用例需覆盖分片不均、部分分片失败、并发探测竞态；排障时从"看一个 key"变成"看 N 个 key 并还原分配过程"。

### 4.6 裁决

**禁止采纳**（净收益为负 + 方案内部自相矛盾）。属于典型的"技术可行但收益不成立"的过度设计。

### 4.7 正确的输出方式

方案主体给基线实现（单 key + Lua 原子扣减），把分片写进**演进预案**章节：

> **演进预案：红包分片**
> - 触发阈值：单个红包的预估峰值并发达到单节点热点 key 上限的 50% 以上（需先用 `redis-benchmark` 压出本机实际上限，不引用未验证数字）。
> - 达到该量级时，**优先手段并非分片**，而是：业务侧削峰（排队/答题/分批放包）、请求侧限流、把金额预分配到应用内存。这些手段成本更低且不与原子性冲突。
> - 仅当上述手段仍不足，且已确认部署形态为多节点 Cluster、并已解决跨槽原子性问题时，才评估分片方案。

### 4.8 同一手段何时净收益为正（正例对照）

分片并非一无是处，它在下列条件下成立：

- 被操作的是**全站级共享热点 key**（如全站热榜计数器、全局秒杀总库存），单 key 压力由全站流量汇聚，确实逼近单节点上限；
- 部署形态为**多节点 Cluster**，且分片数 ≥ 节点数；
- 业务可容忍**最终一致**（如计数类，允许短时误差后聚合校正），或已通过其他机制解决跨槽原子性；
- 读多写少或可接受聚合查询成本（余量查询需遍历分片求和）。

此时收益 = 热点写入吞吐随分片数近似线性提升，成立条件明确，才进入"采纳"档。

## 五、话术黑名单

方案中出现下列表述而无量化支撑时，必须重写该段：

- "提升系统性能" / "增强可扩展性" / "更加健壮"
- "为将来扩展做准备" / "预留扩展点"
- "高并发场景下必不可少" / "业界都是这么做的"
- "有效缓解压力" / "显著优化"

替换公式：**相对基线，本方案使「某指标」从「A」变为「B」，该增量在「某条件/阈值」下成立，代价是「某成本」，故裁决为「采纳/演进预案/禁止采纳」。**
