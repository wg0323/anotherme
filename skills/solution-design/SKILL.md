# 需求落地与技术方案设计规范

## 核心铁律一：搜索先行，禁止臆造

对于任何需求（一个功能点、一个模块、还是一整套系统），在给出任何设计方案或代码之前，必须先在 GitHub / Gitee 上检索同类或相似的成熟开源项目，以其真实的业务建模、架构设计、技术选型作为参考锚点，再结合用户具体场景做适配。**严禁脱离已有工程实践凭空编造方案。**

## 核心铁律二：业界方案优先，简化必须有据

技术选型的默认结论必须是**业界主流方案**——经搜索锚定的、真实生产环境广泛使用的方案。

**严禁以"这是演示代码 / 学习代码 / 本地小项目 / 本地量级用不上"为由，跳过业界方案、直接给出非业界的简化选型。** 理由：学习类/演示类项目的核心收益就是**掌握业界真实做法**；"本地量级用不上其性能"不构成降级理由，用户要学的是方案本身，不是本地量级下的性能数字。

简化方案只有一个合法触发条件：**业界方案受用户本地硬件/资源限制确实无法运行**（见"本地资源受限时的替代方案"）。

### 选型输出顺序（强制）

1. **先呈现业界方案**：是什么（架构/中间件/数据结构）、为什么是它（业界选型理由 + 参考项目锚点）、怎么落到本需求（关键设计）。
2. **再判断是否需要替代**：逐项检查业界方案的资源要求（内存、磁盘、中间件运行时、OS 支持、License）是否与用户本地环境冲突。**默认假设业界方案可以本地运行**——Redis/MySQL/MQ 等主流中间件本地均可轻量运行，不得臆断"本地跑不了"。
3. **能运行就实施业界方案**，即使它为高并发设计、即使本地量级远低于其设计阈值。
4. **确实运行不了才给替代方案**，且必须按"降级路径"的完整格式输出。

## 本地资源受限时的替代方案（降级路径）

仅当业界方案的资源要求与用户本地环境确实冲突（内存不足以运行中间件、环境禁止安装、OS 不支持、商业组件无 License 等），才允许用替代方案实施，且以下结构**缺一不可**：

1. **业界方案完整说明**：即使最终不实施，也必须先完整呈现业界方案，不得省略——用户需要知道"正确的做法长什么样"。
2. **受限说明**：明确指出受限于什么资源（写清"业界方案需要 X，本地环境只有 Y"），不得用"本地开发用不着"这类话术替代。
3. **替代方案与核心差异**：保住了业界方案的哪些语义（数据结构、操作语义、一致性约束），牺牲了哪些（性能、原子性、过期管理、运维特性）。
4. **可替换的抽象边界**：替代实现必须封装在业界方案同样的接口边界之后（如把"连续登录计数器"抽为接口，MySQL 实现与 Redis 实现可互换），让用户资源到位后能低成本切回。
5. **迁移路径**：写清切回业界方案时需要改动的点与步骤。

## 方案收益评估（强制）

**评估对象是"对业界基线的偏离"，而不是业界方案本身。**

业界方案即基线（Baseline）：它是真实生产环境的默认做法，**本身不需要收益论证**——不能用"本地量级用不上 QPS 收益"把业界方案裁决为演进预案。

需要论证的偏离有两类，方向相反、依据不同：

| 偏离方向 | 例子 | 合法依据 |
|----------|------|----------|
| **向上加码**（超出业界方案复杂度） | 业界用单 key + Lua，你上分片；业界用 Redis，你自研缓存 | 必须量化收益（指标增量 + 成立阈值 + 成本清单），走三档裁决，默认禁止 |
| **向下简化**（低于业界方案） | 业界用 Redis，你用 MySQL；业界用 MQ，你用内存队列 | 必须证明业界方案受本地资源限制无法运行，按"降级路径"输出；证明不了就是禁止简化 |

向上加码的量化要求（**技术可行 ≠ 值得实施**）：

1. **收益必须量化**：指明增量落在哪类指标——性能（QPS/TPS、P99 延迟）、资源、可用性、成本、正确性，并给出**数字或数量级**。仅写"提升性能""更健壮"视为无效论证。
2. **收益必须有成立条件**：写清该收益在什么数据量/并发量级、什么部署形态下才生效（**阈值**），低于阈值时收益是多少（通常为 0）。
3. **必须列全成本**：新增代码量与分支复杂度、测试成本、运维与排障难度、新增依赖、一致性/正确性风险、认知成本。
4. **裁决三档**（结论必须三选一并写进方案）：

   | 裁决 | 判定条件 | 处理方式 |
   |------|----------|----------|
   | **采纳** | 净收益为正且阈值在用户量级内可达 | 给出量化预期与生效阈值 |
   | **降级为演进预案** | 收益为 0，或阈值远超真实业务量级 | **不进入实施范围**，写清未来触发阈值与迁移路径 |
   | **禁止采纳** | 净收益为负，或方案内部自相矛盾 | 明确告知用户这是过度设计及原因 |

5. **无法量化时必须标注"未验证推测"**，并给出验证方法，禁止把推测写成结论。
6. **必须做自相矛盾自查**：检查为修复方案副作用而引入的约束，是否恰好抵消了它声称的收益。

量化指标字典、常见优化的生效阈值参考、成本清单、裁决表模板与完整正反例，见 `references/benefit-cost-analysis.md`。该文件五步法中的"基线"一律理解为**业界标准方案**。

## 技术栈与第三方组件选型细则

1. 第三方类库、中间件、工具、框架选型**优先选用开源生态内应用范围广、社区活跃度高、长期维护稳定**的成熟方案，杜绝选用小众无人维护、文档缺失、存在明显安全漏洞且长期未修复的冷门项目。
2. 同等条件下，优先选用 **Apache 软件基金会**旗下官方维护的开源组件与生态方案（如 Apache Commons、Apache Dubbo、Apache RocketMQ、Apache Shiro 等）。
3. 同等条件下，优先选用国内头部企业公开稳定开源、**且当前仍处于活跃维护状态**的技术方案（如 Spring Cloud Alibaba、Nacos、FastJSON2 等），**选型前需验证最新版本发布时间与社区 Issue 响应情况**。
4. 若业务场景无强约束必须使用闭源商业组件，默认优先调研开源替代方案，仅当开源方案确实无法满足需求时，再提供商业软件选型建议。

## 输出要求（强制）

1. **必须列出参考项目清单**：在方案开头以表格或列表形式给出所参考的 1～3 个开源项目，包含项目名称与链接、Star 数/最近更新时间、参考了哪个维度（业务逻辑/架构/技术栈/工程结构）。
2. **必须说明适配差异**：明确指出"参考项目的做法是 X，本方案因用户场景 Y 做了 Z 调整"，让用户知道哪些是照搬、哪些是改造。
3. **多方案对比**：若存在多款可选开源方案，需主动对比核心差异（性能、生态、学习曲线、运维成本）并说明推荐理由，不得私自随意选用非主流方案。
4. **选型结论必须前置业界方案**：结论只能是业界方案，或"业界方案完整说明 + 资源受限的替代实现"双轨；不得只给替代方案而不提业界方案。
5. **必须标注方案定位**：明确当前实施的是"业界方案"还是"资源受限替代方案"，不得把替代方案伪装成业界最佳实践，也不得把业界方案说成"高配/可选"。
6. **必须包含收益/成本裁决表**：对每一个**高于业界基线复杂度**的设计点，逐条给出"业界基线做法 → 本方案做法 → 量化增量 → 成立阈值 → 成本 → 裁决"。
7. **演进预案章节**：量级未达阈值的向上加码设计归入演进预案并写明触发条件，不得塞进实施范围。

## 示例：连续登录需求

- **业界方案（默认实施）**：Redis BitMap（`SETBIT login:{userId}:{yyyy} {当年第几天} 1`）+ `BITCOUNT` 统计登录天数 + 从今天向过去扫描连续 1 得连续天数。业界选它因为：每人每年仅约 46 字节、位运算统计 O(n/8)、可配 key 过期自清理。参考锚点：GitHub Contributions、主流签到系统开源实现。
- **资源受限替代（仅当本地无法运行 Redis）**：MySQL 记录 `(user_id, login_date)` 唯一索引去重，查询时计算连续区间；封装为 `LoginStreakService` 接口，Redis/MySQL 各一实现；写清差异（存储随登录次数线性膨胀、无自动过期、统计变为查询时计算）与迁移路径（新增 Redis 实现类 + 配置切换）。
- **错误示范**：以"演示代码用 MySQL 就够了、Redis 在本地量级没有量化收益"为由直接给 MySQL、只字不提 Redis。

## 禁止事项

- 未做任何搜索就直接给出"我建议你用 XXX 框架搭建 YYY 架构"。
- 编造不存在的库名、项目名、API 接口。
- 仅凭训练数据中的模糊记忆推荐项目，不验证其当前维护状态。
- 将个人偏好伪装为"业界最佳实践"。
- **以"这是演示代码/学习代码/本地量级用不上"为由，跳过业界方案直接选非业界方案。**
- **臆断"本地跑不了某中间件"而不给出具体受限资源，就降级为替代方案。**
- 只给替代方案、不完整呈现业界方案。
- 明知实施的是替代方案，却不标注定位、不说明与业界方案差异、不给迁移路径。
- 输出**高于业界基线复杂度**的设计，却不给出相对基线的增量收益与量化数字。
- 用"提升性能""增强可扩展性""更加健壮""为将来做准备""高并发场景必不可少""业界都这么做"等模糊话术替代收益论证。
- 把只在极端量级下才成立的**加码优化**当作默认方案直接输出。
- 收益为 0 或为负的加码设计不降级为演进预案、直接纳入实施范围。
