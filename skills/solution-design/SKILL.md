# 需求落地与技术方案设计规范

## 核心铁律：搜索先行，禁止臆造

对于任何需求（一个功能点、一个模块、还是一整套系统），在给出任何设计方案或代码之前，必须先在 GitHub / Gitee 上检索同类或相似的成熟开源项目，以其真实的业务建模、架构设计、技术选型作为参考锚点，再结合用户具体场景做适配。**严禁脱离已有工程实践凭空编造方案。**

## 搜索与参考工作流程（每次需求必须执行）

1. **需求拆解**：将用户需求拆解为"业务领域 + 功能类型 + 技术约束"三个维度。
2. **多轮检索**：
   - GitHub 用英文关键词搜索（生态更广），Gitee 用中文关键词搜索（国内业务场景贴合）。
   - 搜索词组合示例：`{领域} + {功能} + {语言/框架}`，如 "workflow engine Java"、"电商 订单系统 Spring Boot"。
   - 至少检索 **2～3 组不同关键词**，避免单一搜索导致视野狭窄。
3. **筛选标准**（按优先级排序）：
   - Stars ≥ 1k（或 Gitee 对应量级）
   - 最近一次 Commit 在 **12 个月以内**
   - 有完善的 README、架构文档或 Wiki
   - Issue 区有人响应，非"死项目"
   - 有实际的 Release 版本或被其他项目依赖引用
4. **参考维度**（从候选项目中提取）：

   | 维度 | 参考内容 |
   |------|----------|
   | 业务建模 | 领域模型、实体关系、核心业务流程拆分 |
   | 架构设计 | 分层方式、模块划分、服务边界 |
   | 技术栈 | 框架组合、中间件选型、数据库方案 |
   | 工程实践 | 目录结构、设计模式运用、异常处理策略 |
   | 部署运维 | 容器化方案、CI/CD、监控告警 |

## 技术栈与第三方组件选型细则

1. 第三方类库、中间件、工具、框架选型**优先选用开源生态内应用范围广、社区活跃度高、长期维护稳定**的成熟方案，杜绝选用小众无人维护、文档缺失、存在明显安全漏洞且长期未修复的冷门项目。
2. 同等条件下，优先选用 **Apache 软件基金会**旗下官方维护的开源组件与生态方案（如 Apache Commons、Apache Dubbo、Apache RocketMQ、Apache Shiro 等）。
3. 同等条件下，优先选用国内头部企业公开稳定开源、**且当前仍处于活跃维护状态**的技术方案（如 Spring Cloud Alibaba、Nacos、FastJSON2 等），**选型前需验证最新版本发布时间与社区 Issue 响应情况**。
4. 若业务场景无强约束必须使用闭源商业组件，默认优先调研开源替代方案，仅当开源方案确实无法满足需求时，再提供商业软件选型建议。

## 方案收益评估（强制）

**技术可行 ≠ 值得实施。** 凡引入额外复杂度的设计（key 分片、分库分表、多级缓存、读写分离、异步化、服务拆分、引入新中间件等），必须先完成收益论证再输出，禁止用"这个方案能跑通"代替"这个方案有收益"。

1. **先立基线（Baseline）**：给出满足当前需求的**最简可行实现**作为对照。方案的收益 = 相对基线的**增量**，而非方案自身的技术先进性。没有基线的收益论证一律无效。
2. **收益必须量化**：指明增量落在哪一类指标上——性能（QPS/TPS、P99 延迟）、资源（内存/连接数/CPU/存储）、可用性（故障影响面、恢复时间）、成本（人力/运维/机器），并给出**数字或数量级**。仅写"提升性能""更健壮""易于扩展"视为无效论证。
3. **收益必须有成立条件**：写清该收益在什么数据量/并发量级、什么部署形态下才开始生效（**阈值**），以及低于阈值时收益是多少（通常为 0）。
4. **必须列全成本**：新增代码量与分支复杂度、测试成本、运维与排障难度、新增依赖、引入的一致性/正确性风险、团队认知成本。
5. **裁决三档**（结论必须三选一并写进方案）：

   | 裁决 | 判定条件 | 处理方式 |
   |------|----------|----------|
   | **采纳** | 净收益为正 | 给出量化预期与生效阈值 |
   | **降级为演进预案** | 收益为 0，或无法验证 | **不进入实施范围**，写清未来触发阈值与迁移路径 |
   | **禁止采纳** | 净收益为负，或方案内部自相矛盾 | 明确告知用户这是过度设计及原因 |

6. **无法量化时必须标注"未验证推测"**：收益结论若无公开基准数据、参考项目实测数据或本地压测支撑，必须显式标注为推测，并给出验证方法（如用 `redis-benchmark` 压测热点 key 上限），禁止把推测写成结论。
7. **必须做自相矛盾自查**：检查为修复该方案副作用而引入的约束，是否恰好抵消了它声称的收益（典型：为保原子性把分散的 key 用 hash tag 锁回同一分片，则"分散热点"的收益直接归零）。

量化指标字典、常见优化的生效阈值参考、成本清单、裁决表模板与完整正反例，见 `references/benefit-cost-analysis.md`。

## 输出要求（强制）

1. **必须列出参考项目清单**：在方案开头以表格或列表形式给出所参考的 1～3 个开源项目，包含项目名称与链接、Star 数/最近更新时间、参考了哪个维度（业务逻辑/架构/技术栈/工程结构）。
2. **必须说明适配差异**：明确指出"参考项目的做法是 X，本方案因用户场景 Y 做了 Z 调整"，让用户知道哪些是照搬、哪些是改造。
3. **多方案对比**：若存在多款可选开源方案，需主动对比核心差异（性能、生态、学习曲线、运维成本）并说明推荐理由，不得私自随意选用非主流方案。
4. **必须包含收益/成本裁决表**：对每一个高于基线复杂度的设计点，逐条给出"基线做法 → 本方案做法 → 量化增量 → 成立阈值 → 成本 → 裁决"，裁决只能是采纳/演进预案/禁止采纳三者之一。
5. **默认输出最简方案**：以基线方案作为实施内容，把高配设计放进"演进预案"章节，并写明触发阈值（如"当单红包峰值并发预估超过 X QPS 时再启用"），不得把用户当前量级用不到的设计直接塞进实施范围。

## 生产级方案对照说明（强制）

1. **标注方案定位**：明确说明当前方案属于"生产级方案"还是"因 demo/本地环境/快速验证而简化的方案"，不得把简化方案伪装成生产级最佳实践。
2. **给出生产级对照**：若当前方案为简化版，必须用文字补充真实生产环境/业界主流做法——采用什么架构与中间件、为何这样选、与简化版的关键差异、上生产需补齐的环节（如高可用、水平扩展、监控告警、数据一致性、安全加固）。
3. **对照需有锚点**：生产级对照同样遵循"搜索先行"，尽量引用前述参考开源项目中的真实生产实践，而非凭空描述。
4. **区分"简化方案"与"最简基线"**：两者不得混淆。简化方案 = 因 demo/快速验证而**砍掉了必要环节**（如缺幂等、缺异常处理），属缺陷，必须补齐或明示；最简基线 = 满足真实需求前提下**复杂度最低**的完整正确实现，属应当默认交付的目标。本章要求的是补齐前者，而非把后者升级为高配方案。
5. **与收益评估的衔接**：生产级做法属于"告知义务"，用文字对照说明即可；是否纳入实施范围，仍由"方案收益评估"的裁决决定——量级未达阈值的生产级手段一律归入演进预案。

## 禁止事项

- 未做任何搜索就直接给出"我建议你用 XXX 框架搭建 YYY 架构"。
- 编造不存在的库名、项目名、API 接口。
- 仅凭训练数据中的模糊记忆推荐项目，不验证其当前维护状态。
- 将个人偏好伪装为"业界最佳实践"。
- 明知方案是简化/demo 版，却不告知用户真实生产级/业界主流做法，或把简化方案包装成生产级最佳实践。
- 输出高于基线复杂度的设计，却不给出相对基线的增量收益与量化数字。
- 用"提升性能""增强可扩展性""更加健壮""为将来做准备""高并发场景必不可少""业界都这么做"等模糊话术替代收益论证。
- 把只在极端量级（远超用户实际业务规模）下才成立的优化，当作默认方案直接输出。
- 收益为 0 或为负仍将其纳入实施范围，而不降级为演进预案。
- 只论证方案"能实现"，未论证方案"有对价"，导致代码复杂度白增。
