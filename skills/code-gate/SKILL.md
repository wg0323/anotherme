# 代码交付门禁

AI 写代码、AI 写测试、AI 跑测试、AI 说通过——判断主体始终是同一个模型。本技能只做一件事：**在交付前补上生成者之外的判定信号**。它不管"怎么写"（归各技术栈规范技能），也不管"怎么跑"（归 `test-execution`）。

## 核心铁律

1. **生成者自证不算证据**。交付前自检清单、AI 自己勾的核对项、`Tests run` 全绿，都不能单独构成可交付结论。每份交付至少给出 1 条外部信号：编译、架构断言、变异测试、契约 diff、独立审查。
2. **先分级再验收**。任何改动先判 A/B/C 级（见下表）。B 级必须逐行读懂才能合并，读不懂就拆小到读懂；不得以"测试过了"为由跳过 B 级阅读。
3. **测试全绿 ≠ 测试有效**。覆盖率统计的是"被测代码有没有被执行"，AI 照自己的错误理解写测试同样能拉满覆盖率。B 级核心逻辑必须有变异测试或独立审查，二者至少其一。
4. **门禁只对新代码生效**。存量违规用 `FreezingArchRule` 冻结或白名单隔离，不追缴历史代码；否则首次接入即满屏告警，规则会被整体关掉。
5. **规则按真实事故准入**。每条门禁规则必须能对应一次真实缺陷或事故；写不出对应事故的规则不进构建。
6. **交付必须给证据**，固定「命令 → 关键输出 → 结论」三段式，禁止只写"已完成""已修复""测试通过"。
7. **强制声明不确定点**。交付时列出需求歧义、未经核实的 API 与版本、跳过的分支、未验证的假设。审代码的人按这份清单审，不按全部代码审。
8. **超规模改动必须拆分**。单次改动超过 400 行或 10 个文件（按自身审查带宽设阈值，但必须有阈值）先拆块。超过人的审查带宽后，审查等于没审查。

## 改动分级

| 级别 | 判定条件（任一命中） | 你的义务 | 最低验收 |
| --- | --- | --- | --- |
| A 可委托 | 纯 CRUD、DTO/VO 映射、配置项、样式、日志文案、注释与文档 | 不要求逐行读懂 | 机械门禁 + 冒烟 |
| B 必须读懂 | 鉴权与资源归属、金额计算、状态流转、事务边界、幂等、并发、消息可靠投递、DB 结构与索引变更、缓存一致性、外部支付与短信 | 逐行读懂，读懂是合并门槛 | 机械门禁 + 变异测试或独立审查 + 冒烟 |
| C 禁止外包 | 数据迁移脚本、生产环境配置、密钥与凭据、批量删改数据 | AI 只出方案，人执行 | 人工复核后执行 |

定级规则：跨级取高不降级；改动落在公共组件（工具类、拦截器、DTO、配置 key）按 B 级处理，不按改动行数定级；判不准按 B 级。

## 四类外部信号

| 信号 | 适用级别 | 通过判据 |
| --- | --- | --- |
| 机械门禁 | 全部 | 编译零错误，架构断言全绿 |
| 变异测试 | B 级核心模块 | 变异得分 ≥ 70%，存活的变异体逐条给出理由 |
| 契约比对 | 动了 API / DB / MQ | 快照 diff 可解释，无未声明的破坏性变更 |
| 独立审查 | B 级 | 审查者只看 diff 与需求，不看实现者说辞；无阻断级问题 |

## 交付证据格式

```text
【改动分级】B（鉴权与资源归属）
【机械门禁】mvn test -Dmaven.test.skip=false → ArchitectureTest 4 rules, Failures: 0
【变异测试】mvn org.pitest:pitest-maven:mutationCoverage → mutation score 78%
【契约比对】openapi.json diff → 新增字段 userLevel，向后兼容
【独立审查】新会话 review diff → 1 条阻断（事务跨远程调用），已修复
【不确定点】1. 未核实 xxx 版本是否存在，按 yy 假设；2. 分页最大条数未确认
【未覆盖】短信发送失败分支无可用测试环境
```

无对应信号的条目写「未执行 + 原因」，不省略、不合并。

## 禁止事项

- 用"我已检查""代码符合规范"代替可执行证据。
- 用行覆盖率代替变异得分，或为凑覆盖率写无断言测试。
- B 级改动只跑测试不读代码就合并。
- 为让门禁通过而删规则、加 `@ArchIgnore`、放宽阈值，且不记录原因。
- 让 AI 自行定级后无人复核——分级结论必须写在交付证据首行。
