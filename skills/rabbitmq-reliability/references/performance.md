# 吞吐量权衡与验证

先确定消息是否允许丢失、需要抗哪些故障，再通过异步化和参数调优达到吞吐目标。不要先关闭 Confirm、持久化或幂等，再用压测数字证明它“更快”。

## 各项机制的实际代价

| 机制 | 主要成本 | 落地方式 |
| ---- | ---- | ---- |
| correlated Confirm | 网络和确认处理；持久化、复制会延长 ACK | 保留异步流水线，不逐条阻塞等待 |
| persistent 消息 | 磁盘写入和批量刷盘延迟 | 不允许丢失的消息保留，可丢弃采样数据另行分级 |
| quorum queue | 多数派复制、网络与磁盘开销 | 用于需要抗 Broker 单节点故障的队列 |
| mandatory / Return | 正常路由路径开销较小 | 不允许丢失的消息保留，Return 更新 Outbox |
| `prefetch=1` | 无法形成有效投递流水线 | 按压测提高，同时限制未 ACK 数和内存 |
| 消费本地重试 | 故障期间占用消费线程 | 只处理临时异常，长退避移出本地线程 |
| 数据库事务幂等 | 唯一索引写入和事务开销 | 核心消息保留，可批量处理时合并数据库操作 |
| Redis 前置去重 | 额外网络往返 | 作为优化层，不替代数据库原子幂等 |
| 逐条成功 INFO 日志 | 日志格式化与磁盘 I/O | 改为指标，日志用于失败和抽样诊断 |
| JSON 序列化 | CPU 和消息体积 | 保持 DTO 精简，大文件传引用 |

durable 声明、heartbeat 等不是常规吞吐瓶颈，不应作为性能优化对象。

## 调参顺序

1. 保持 Confirm 异步，使用 Outbox 投递任务解耦业务请求与 Broker 确认延迟。
2. 调整 `prefetch`。可从 20 或 50 开始，对快速处理任务继续测试 100～300；处理慢、消息大或内存紧张时降低。
3. 调整消费者并发。同时检查 CPU、数据库连接池、下游限流和消息顺序，不能只增加 RabbitMQ 并发数。
4. 缩短业务处理时间，减少串行远程调用。数据库批量提交与 Outbox 批量状态更新可以降负载，但必须接受崩溃后的重复投递。
5. 成功路径减少逐条日志；重试采用退避和随机抖动，避免故障恢复时形成重试尖峰。
6. 单队列达到瓶颈后按业务键拆分队列。同一业务键有顺序要求时仍进入同一队列，不能为了并发破坏顺序。

prefetch 越大，消费者崩溃时可能重投的在途消息越多，内存占用也越高。吞吐量、故障重放量和内存上限需要一起评估。

## 压测与监控

压测使用项目实际 RabbitMQ 和 Spring AMQP 版本、集群节点数、磁盘、网络、消息大小及真实消费逻辑。分别记录：

- 发布速率、消费速率、吞吐量和消息大小；
- Confirm 延迟与消费端到端延迟的平均值、p95、p99；
- Queue ready、unacked、consumer capacity 和消费者处理耗时；
- Outbox 待发送数量、最老记录年龄、Confirm 超时数量；
- Broker CPU、内存、磁盘利用率和复制状态；
- 重试率、重复率、DLQ 数量、告警与补偿耗时。

不能只观察 Broker 空闲时的吞吐。还要制造消费者变慢、下游限流和短时连接中断，确认 backlog 能恢复且不会无限重试。

## 上线前故障演练

至少验证以下窗口，并检查最终业务状态和幂等记录：

- 业务与 Outbox 已提交，应用尚未发布就崩溃；
- Broker 已接收消息，生产者收到 Confirm 前断线；
- 路由不存在导致 Return，以及 Return 后收到 ACK 的回调顺序；
- 消费者业务已提交，但 ACK 前崩溃；
- 同一消息并发重复投递；
- 临时下游故障、重试耗尽、DLQ 落库失败和修复后的重放；
- quorum 单节点停机和恢复，确认集群仍满足多数派。

演练通过标准是业务记录最终正确、无未解释的 Outbox/DLQ 滞留、重复消息不会再次产生业务效果。仅以“控制台没有报错”作为通过条件不够。

参考：[RabbitMQ Confirms and Prefetch](https://www.rabbitmq.com/docs/confirms) 与 [Quorum Queues](https://www.rabbitmq.com/docs/quorum-queues)。
